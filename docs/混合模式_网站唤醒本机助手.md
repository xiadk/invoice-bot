# 混合模式：网站 + 本机 Electron 助手

> **一句话**：用户登录你的网站，点「批量发送」→ 网站把本机 Electron 助手拉起来 → 助手连回服务器领任务 → 在它自带的浏览器里驱动 1688 发送 → 进度回传网站。
>
> **本质**：这就是**方案C，把「浏览器扩展」换成「Electron 桌面助手」**。浏览器无关的弱点没了，商店审核也没了；代价是仍要装一次桌面程序。

---

## 0. 直接回答可行性

**可行，而且是你现有架构里改动最小的一条路。**

理由：你现在的服务端已经为「本机执行器」设计好了全套接口，只差一个**换客户端**：

| 现有设施 | 位置 | 换 Electron 后 |
|---|---|---|
| 长连接中枢（注册表/心跳/在线状态） | `lib/agent-hub.js` | **不用改**，助手连同一个 `/ws/agent` |
| 配对接口（配对码 = 税号，永不过期） | `POST /api/agent/pair-code` | **不用改**（建议加个 device token，见 §7） |
| 在线状态 | `GET /api/agent/status` | **不用改** |
| 任务下发 | 已有 `send_batch`（WS 下行） | **不用改** |
| 进度/停止协议 | 已有 `task_progress` / `client_stop` / `sent` | **不用改** |
| 断线续跑/对账 | 已有 `/api/agent/resumable`、`/api/agent/resume`、`agent_task` 表 | **不用改** |

而助手端要写的代码，**`extension/background.js` 可以直接移植**（见 §5 的映射表）——它已经是一份完整的助手客户端：连接、保活、收 `send_batch`、开工作页、找编辑器 frame、发送、回报、停止。

**唯一需要全新设计的是「唤醒」这一段**（§3），因为网页无法直接启动本地程序，必须走自定义 URL 协议。

## 1. 三种形态的关系（先摆清定位）

| | 扩展版（方案C 现状） | **混合版（本方案）** | 纯单机版（Electron版实施方案） |
|---|---|---|---|
| 用户要装 | 浏览器扩展 | **桌面 exe** | 桌面 exe |
| 装完还要做 | 填服务器地址 + 税号配对 | **点一次「绑定」，之后全自动** | 无 |
| 数据存哪 | 你的服务器 | **你的服务器** | 用户本地 |
| 网站角色 | 控制台 + 数据 + 任务 | **控制台 + 数据 + 任务 + 唤醒入口** | 无（或仅授权） |
| 商业模式 | 订阅 SaaS | **订阅 SaaS** | 买断 |
| 商店审核 | ⚠️ 受 Chrome/Edge 政策约束（Bots 条款是硬伤） | ✅ **不受商店政策约束** | ✅ 不受约束 |
| 1688 风控 | 低（真实 IP） | **低（真实 IP）** | 低（真实 IP） |
| 数据丢失售后 | 无（数据在你这） | **无（数据在你这）** | 有（重装即丢，你无法代恢复） |
| 更新分发 | 商店静默更新 | **electron-updater 自动更新** | 同左 |

**这个模式最大的隐性收益**：自动化行为从「浏览器扩展」搬到「桌面程序」，**直接绕开了商店的 Bots 条款**——那是上一轮调研里判定「上架风险很高」的根因。桌面程序不受 Chrome/Edge 商店政策管。

## 3. 【核心】怎么「唤醒」本机应用

浏览器的安全模型**不允许网页随意启动本地程序**，唯一的合法通道是**自定义 URL 协议**，且**必须由用户点击触发**——你正好有「点击批量发送」这一下，天然满足。

### 3.1 主机制：自定义协议 `invoicebot://`

**注册（Windows，免管理员）**：写入 `HKCU\Software\Classes\invoicebot`，`shell\open\command` = `"C:\...\invoice-bot.exe" "%1"`。
- `electron-builder` 的 `build.protocols` 字段可在安装时自动注册，无需手写注册表。
- 用 **HKCU**（当前用户）而非 HKLM，**不需要管理员权限**。
- 卸载时由安装器自动清理（portable 版**不会注册协议** → 这是 portable 的一个真实短板，见 §6）。

**触发**：网页里 `location.href = 'invoicebot://run'`。

**两个必须知道的浏览器行为**：
1. **首次会弹确认框**：「此网站尝试打开『催收小助手』，是否允许？」——无法绕过，但 Chrome/Edge 会记住选择。
2. **未安装则静默失败**（控制台报错，页面无感知）→ 必须主动检测 + 回退（§3.2）。

### 3.2 在线检测：**推荐走服务端，不要让网页直连 localhost**

| 方式 | 做法 | 判定 |
|---|---|---|
| **服务端判定（推荐）** | 助手连着 `/ws/agent` → 网页查 `GET /api/agent/status` | ✅ 零浏览器限制、零端口冲突、已有接口 |
| 网页直连 localhost | `fetch('http://127.0.0.1:17871/health')` | ⚠️ 受 **Private Network Access 预检**限制（需 HTTPS 页面 + 服务端回 `Access-Control-Allow-Private-Network: true`）；固定端口易冲突；**不建议** |

**所以网页根本不需要碰本地网络**——它只调自己的服务端，由服务端告诉它「助手在不在线」。这既避开了 PNA 那一堆坑，也让安全边界更干净。

### 3.3 完整时序（点「批量发送」之后）

```
用户点击「批量发送」
  │
  ├─1 页面查 /api/agent/status
  │     ├─ online  ─────────────────────────────────────┐
  │     └─ offline ─▶ location.href = 'invoicebot://run' │  （用户点击手势 → 允许）
  │                    │                                │
  │                    ├ 浏览器确认框（首次）             │
  │                    ├ 系统拉起 invoice-bot.exe（冷启动数秒）│
  │                    └ 助手读本地已存凭证 → 连 /ws/agent → online
  │                                                      │
  │       页面显示「正在启动本机助手…」，轮询 status 直到 online │
  │       （超时 30s → 提示「未检测到助手，点此安装 / 手动启动」）│
  │                                                      ▼
  ├─2 页面 POST /api/send  ──▶ 服务端建 agent_task、组装 sellers+messages
  │                              │
  │                              └─▶ agentHub.send(uid, {type:'send_batch', taskId, sellers, gapMs})
  ├─3 助手执行：逐个 seller 打开聊天页 → 注入脚本发送 → 回报
  │       每个 seller 完成 → ws: {type:'sent', taskId, loginId, ok, error}
  │       服务端写 send_log + 记 agent_task + 推 {type:'task_progress'} 给网页
  ├─4 网页实时渲染（当前卖家 / 进度条 / 成功失败数 / 停止按钮）
  │       点「停止」→ POST /api/task/stop → 服务端 ws: {type:'stop'} → 助手置 stopFlag
  │       助手也会回报 {type:'client_stop'} 表明是本机主动停的
  └─5 全部结束：汇总；断线/关网页也不怕——agent_task 表在，可 /api/agent/resume 续跑
```

## 4. 服务端改动清单（几乎为零）

| 项 | 改动 |
|---|---|
| `lib/agent-hub.js` | **不改**（`meta` 里的 `extVer/platform` 字段改叫 `agentVer/os` 即可，纯文案） |
| `/ws/agent` 连接层 | **不改**（`redeem(code)` 仍是税号→userId） |
| `/api/agent/pair-code` | **不改**（返回税号 + serverUrl，正好可供深链拼接） |
| `/api/send`、`/api/task/stop`、`/api/agent/status`、`/api/agent/resume` | **不改** |
| 新增 `GET /download` 落地页 | 改为引导下载 exe（现有 `download.html` 改造，去掉「加载扩展」文案） |
| 新增（可选）`POST /api/agent/device` | 若启用 device token 加固（§7），加一个签发表 |
| `extension/` 目录 | 保留（老用户还能用），或标注「即将下线」 |

## 5. 助手端移植映射表（`extension/background.js` → Electron）

好消息：**服务端协议一行都不用改，助手端照着搬**。API 对照：

| 扩展 API（background.js） | Electron 等价物 |
|---|---|
| `new WebSocket(url)` | Node 22 原生 `WebSocket`（或 `ws` 包）——**代码几乎不变** |
| `chrome.storage.local.get/set` | 本地 JSON 配置文件（`app.getPath('userData')/agent.json`） |
| `chrome.tabs.create({url})` | `new BrowserWindow({...})` |
| `chrome.tabs.update(tabId,{url})` | `win.loadURL(url)` |
| `chrome.tabs.sendMessage(tabId, msg, {frameId})` | `frame.executeJavaScript(script)`（`webContents.mainFrame.frames` 递归定位聊天 frame） |
| `chrome.webNavigation.getAllFrames({tabId})` | `webContents.mainFrame.framesInSubtree` |
| `chrome.alarms.create(periodInMinutes:1)`（保活） | `setInterval` + 托盘常驻——**MV3 SW 被杀/保活那套麻烦直接消失** |
| `chrome.action.setBadgeText` | 托盘图标状态（Tooltip / 图标变色） |
| `chrome.runtime.onMessage`（popup/各 frame） | `ipcMain` + 助手自己的小窗口 |
| `content.js` 的 `sendOne/sendMessages` | **原样搬**（纯 DOM 操作）→ `inject.js` |

**要新写的只有三块**：① 托盘 + 小窗口 UI（连接状态 / 登录态 / 停止）；② 深链协议解析（`app.setAsDefaultProtocolClient` + `second-instance` 事件）；③ 登录态预检（用聊天页编辑器是否出现来判定，`content.js` 里已有这段逻辑）。

## 6. 必须处理的坑（都是真实会遇到的）

| # | 坑 | 处置 |
|---|---|---|
| 1 | **深链首次确认框** 吓到用户 | 文案写成「点『打开』即可」，配图；确认一次后浏览器记住 |
| 2 | **未安装时点了没反应** | 先查 `/api/agent/status`；offline 且多次拉起失败 → 弹「未检测到本机助手 → 下载」引导页 |
| 3 | **冷启动等待**（点完要 2~5s 才 online） | 网页显示「正在启动本机助手…」+ 30s 超时 + 重试按钮；**别让用户以为卡死** |
| 4 | **portable 版无法注册协议** | 主推 **nsis 安装版**；portable 版只能手动启动助手（作降级） |
| 5 | **同机多账号** | 助手应绑定一个身份；检测到切号要明确提示（一个浏览器 profile 只登一个 1688 号） |
| 6 | **助手未常驻**（用户没开、开机没自启） | 每次深链都会拉起；提供「开机自启」选项；托盘常驻是默认 |
| 7 | **协议被劫持**（别的程序抢注 `invoicebot://`） | 深链**只传意图、不传敏感数据**（§7）；助手连服务器时用自己存的凭证 |
| 8 | **杀软误报 / SmartScreen** | 同 Electron 方案：MVP 先不签名 + 图文放行指引；正式发售前上签名证书 |
| 9 | **卸载残留** | 安装器负责清 `HKCU\Software\Classes\invoicebot` 与自启项 |

## 7. 安全：必须修的一个现有弱点

**现有配对码 = 公司税号（`app_user.tax_no`），永不过期。** 对扩展来说这只是「麻烦」；对桌面版来说这是**数据泄露**风险：

> 税号是半公开信息（印在发票上、可查）。**任何人拿到你的税号，就能起一个助手用你的身份连上服务器**；一旦你点发送，任务（含你的订单号、金额、发票明细、催收文案）会被下发到**攻击者的助手**。

**建议（与本次改造一并做）**：从「税号当配对码」升级为**设备令牌**：

```
安装/绑定时：网页 POST /api/agent/pair-code  → 服务端签发一次性 token（60s TTL）
            深链 invoicebot://bind?server=<url>&t=<token>
            助手拿 token 调 POST /api/agent/device → 换取长期 device_token（存本地）
之后：助手连 /ws/agent?device=<device_token>（不再用税号）
     服务端：token 有效 → 查 agent_device 表 → userId；可在后台「踢设备」
```

好处：税号不再能当凭证；可在后台看到「该账号绑定了哪些设备」并逐个踢下线；老板换电脑也能自助。**改动很小（一张表 + 两个接口）**，但补掉了一个真实的洞。

**其余安全底线不变**：服务器不保存 1688 登录态；助手只上报「是否已登录」布尔值；助手不自建账号体系；深链不携带任务内容。

## 8. 里程碑（在「纯单机版」基础上调整）

| 阶段 | 内容 |
|---|---|
| **N0** | 服务端**几乎零改动**：确认 `/ws/agent` 与 `/api/agent/*` 可用；把下载页从「装扩展」改为「装 exe」 |
| **N1** | **助手骨架**：Electron 托盘 + `agent.json` 凭证 + WS 客户端（照搬 `background.js`）+ 在线状态上报 → 网站能看到「助手在线」 |
| **N2** | **发送内核** ⭐：发送窗（`persist:1688`）+ UA 伪装 + `inject.js`（照搬 `content.js`）+ `send_batch` 执行 + `sent` 回报 → **用真实账号跑通 1 个卖家，再跑 1 批** |
| **N3** | **唤醒链路**：注册 `invoicebot://` + 深链解析 + 网页「批量发送」自动拉起 + 冷启动等待/超时/未安装回退 |
| **N4** | **device token 加固**（§7）+ 后台「设备管理/踢设备」 |
| **N5** | **打包与自动更新**：nsis + `electron-updater` + 签名（发售前）+ 放行指引页 |
| **N6** | 硬化：文案随机化、失败退避、诊断包导出 |

**关键路径仍是 N2（发送内核）**——N1/N2 可以先本地跑通，不依赖 N3 的唤醒。

## 9. 这个模式 vs 纯单机版：怎么选

| 若你最在意… | 选 |
|---|---|
| 订阅收费、统一看板、数据在你手、无「重装丢数据」售后、自动化不受商店政策约束 | **混合版（本文）** |
| 离线可用、极致隐私、彻底不管服务器、无需常驻进程 | 纯单机版 |
| 破解除成本（抗逆向） | 都偏弱；纯单机版更难被「服务器端封杀」，混合版更难被「本地破解授权」 |

**两者其实可以共存**（同一个 Electron 程序：有账号时走混合模式，无账号时走本地模式），但会**双倍复杂度**——v1 建议只做一条。
