# 需求

1. 点「登录 1688」→ 引导用户**在自己电脑的浏览器**登录 → 获取登录态 → **保存到数据库**
2. 点「发送催收」→ **从数据库获取该用户登录态** → 调用部署机器上的浏览器发送催收消息
3. **服务器不再承载登录画面**（去掉投屏登录）：服务器全程接触不到 1688 密码

# 结论（TL;DR）

| 项 | 结论 |
|---|---|
| 可行性 | **高**，已落地。本质是把「登录态的存储介质」从文件换成数据库，**发送链路本身没改**，只是把「态从哪来」换了个来源 |
| 关键技术依据 | Playwright `newContext({ storageState })` 既接受**文件路径**也接受**对象** → 从库解密出来**直接喂给浏览器，无需临时文件**（已实测：`stateFrom='object'`） |
| 登录方式 | **用户本机登录 + 扩展上传登录态**（方案 B）。密码不过服务器；登录用用户真实 IP，风控更友好 |
| 落地形态 | 新增 `login_state` 表 + `lib/state-store.js`（AES-256-GCM）+ `/api/state/*` 四个接口 + 扩展「上传登录态」+ 看板引导弹窗；**删除 `lib/live-browser.js` 与全部投屏登录代码** |
| 验证 | 登录态 e2e **35/35**、看板 UI **20/20**、方案C 回归 **55/55 + 18/18** |
| 真正难点 | 不是可行性，而是**安全**（库里存 cookie = 存账号凭据）与**密钥管理** |

# 2 目标（to-be）

> **登录态成为一条数据库记录；发送时从库取，服务端本机浏览器加载后发送。文件降级为可选缓存。**

```
点「登录 1688」→ 看板生成一次性上传码（10 分钟有效，用后即焚）
   → 用户在自己电脑的浏览器登录 1688（通常本来就登录着）
   → 浏览器扩展读取 cookie(+httpOnly) 与页面 localStorage，组装成 storageState
   → POST /api/state/upload（凭上传码，无需看板会话）
   → AES-256-GCM 加密 → UPSERT login_state(user_id, '1688')

点「发送催收」 → SELECT login_state → 解密 → launch({ storageState: obj })
   → 逐家发送 → recordSent（成功则 touch，被跳登录页则 markExpired）
```

**服务器全程不承载登录画面**：没有任何 CDP 投屏、没有输入回灌、服务器看不到密码，也不需要用户把账号密码交给第三方页面。

# 3 设计

## 3.1 数据模型：新表 `login_state`（一人一平台一行）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT UNSIGNED PK | |
| `user_id` | INT UNSIGNED | 归属用户 |
| `platform` | VARCHAR(16) | 默认 `'1688'`（预留多平台） |
| `state_enc` | MEDIUMTEXT | AES-256-GCM 密文，格式 `v1:<keyId>:<iv>:<tag>:<cipher>`（base64） |
| `key_id` | VARCHAR(16) | 密钥版本号，支持轮换 |
| `cookie_count` / `origin_count` | INT | 完整性自检，不泄露内容 |
| `status` | ENUM('active','expired','invalid') | 失效检测结果 |
| `source` | ENUM('cloud_login','extension','migrated','manual') | 来源 |
| `saved_at` | DATETIME | 写入时间（**替代原文件的 mtime**） |
| `last_used_at` / `last_checked_at` | DATETIME | 发送使用 / 失效校验时间 |
| `created_at` / `updated_at` | DATETIME | |
| `UNIQUE KEY (user_id, platform)` | | 一人一行，UPSERT；`KEY (status)` 便于巡检 |

> 用 `MEDIUMTEXT` 而非 `JSON`：内容是**密文**（base64），不是结构化数据，加密后 JSON 类型也失去索引/查询意义。

## 3.2 写入路径（实现）

| 位置 | 实际做法 |
|---|---|
| `lib/state-store.js` | **新增**：`saveState(userId,obj,{source})` / `loadState(userId)` / `getMeta(userId)` / `hasActiveState` / `clearState` / `touch` / `markExpired` / `migrateFromFiles` / `startupNotices`；内部加解密 + UPSERT |
| 扩展 `background.js` | `chrome.cookies.getAll({domain:'1688.com'})` 取 cookie（含 httpOnly，`sameSite` 映射为 `None/Lax/Strict`，`expirationDate`→`expires`，会话cookie→`-1`）；`chrome.scripting.executeScript` 从已打开的 1688 标签页取 `localStorage` 作为 `origins`；`POST {serverUrl}/api/state/upload` |
| `server.js#POST /api/state/upload` | 先做形状校验（空态直接 400，**不消耗**上传码）→ `redeemUploadToken` → `stateStore.saveState(uid, state, {source:'extension'})`。**放在登录闸门之前**（扩展没有看板会话 Cookie） |
| `POST /api/state/upload-token` | 生成 6 位一次性上传码（TTL 10 分钟；同用户旧码作废），返回 `{code, ttlSec, expiresAt, serverUrl}` |

> 扩展上传走的是一次性码，**不是**看板会话：因此该接口必须公开（并带 CORS），否则扩展永远 401。

## 3.3 读取路径（实现）

| 位置 | 实际做法 |
|---|---|
| `lib/browser.js#launch(options)` | 新增 `options.storageState`（对象）。优先级：**`storageState` 对象 > `statePath` 文件 > 无**；返回值新增 `stateFrom: 'object'|'file'|'none'` 便于排查 |
| `server.js#doSend` | `const st = await stateStore.loadState(userId)`；`launch({ statePath, storageState: st })`；日志区分「已从账号（数据库）取到登录态」；**成功后 `stateStore.touch(userId)`**、**捕获「登录态失效」→ `stateStore.markExpired(userId)`** |
| `server.js#stateStatus(userId)` | 取代原 `liveStatus`：改读库，返回 `hasState / usable / status / source / savedAt / lastUsedAt / cookieCount / originCount`；**不含密文** |
| CLI 脚本（4 个） | 一期**保持读文件**（兼容不改）；二期统一走 state-store（加 `--user <id>`） |

## 3.4 迁移（无损、幂等）

1. `db.js` 迁移里**幂等建表** `login_state`。
2. 某用户库中无记录、而文件 `state-1688.json` 存在 → 读文件 → 加密入库，`source='migrated'`。
3. **不删文件**（回滚安全）。读取时**优先库**，库为空才回退文件。
4. 提供 `node scripts/state-export.js --user <id>`（导出排查）与 `--rekey`（换密钥）。

## 3.5 安全（本方案的核心）

| 项 | 设计 | 实现 |
|---|---|---|
| 静态加密 | AES-256-GCM；`iv` 12B 随机；`authTag` 随密文；单字段自描述格式 `v1:<keyId>:<iv>:<tag>:<cipher>`（base64url） | ✅ `lib/state-store.js` |
| 密钥 | 32B 密钥由密钥串 `sha256` 派生；`keyId` = 前 8 位 hex。**优先环境变量 `STATE_SECRET`**；未配置则首次随机生成并写入 `data/.state-secret(0600)`，**启动时打印告警**（不静默降级、不阻断启动） | ✅ `startupNotices()` |
| 轮换 | `key_id` 多版本：读按 keyId 选密钥，写用当前版本；`STATE_SECRET_OLD`（逗号分隔）可解密旧数据 | ✅ |
| 权限 | 密文**只对本人**返回；管理员看板/查询仅见**元信息**（是否有效、何时存），**绝不下发密文** | ✅ 实测：`/api/state/status` 无 `state_enc` 字段 |
| 日志 | 禁止打印 cookies / 密文；只打印「N 个 cookie / M 个源」 | ✅ |
| 传输 | 保持 HTTPS；扩展上传走一次性码 + CORS 白名单方法 | ✅ |
| 备份 | 备份含密文 = 含凭据：备份文件按机密管理；**泄库且泄密钥**才可利用（两层防护） | 部署约定 |

## 3.6 失效与刷新

| 场景 | 行为 |
|---|---|
| 发送时页面跳登录页 | 捕获 → `status='expired'` → 中止本次并提示重新登录 |
| 任意一次发送成功 | `last_used_at=now`、`status='active'`（自愈） |
| 用户重新登录保存 | UPSERT 覆盖，`status='active'` |
| `POST /api/browser/clear` | 清库中登录态（下线/换号用） |
| 定时探活（可选·二期） | 每日轻量请求探活，失效则给用户提醒 |

# 7 风险与对策

| 风险 | 级别 | 对策 |
|---|---|---|
| 库里存 cookie = 存账号凭据 | **高** | AES-256-GCM + 密钥环境变量 + 仅本人可见 + 备份按机密管理 |
| 密钥丢失 / 容器重建后随机密钥 | **高** | 优先强制 `STATE_SECRET`（未配则用 `data/.state-secret` 并**启动告警**）；`key_id` 多版本轮换 + `STATE_SECRET_OLD` 解密旧数据 |
| 用户在服务器上登录带来的凭据暴露 | **已消除** | 方案 B：**去掉投屏登录**，登录只发生用户本机，服务器不承载登录画面、拿不到密码 |
| 服务器 IP 集中登录触发风控 | **已消除** | 登录用用户本机真实 IP |
| 登录态体积偏大 | 低 | `MEDIUMTEXT`；实测 1688 storageState 通常 5~30KB（base64 后 ×1.35） |
| 与方案C 并存导致概念混淆 | 中 | 明确：本方案 = **服务端本机浏览器**通道；方案C = 用户自带浏览器 |
| CLI 脚本仍读文件 | 低 | 一期双写兼容；二期统一 |

# 8 口径（已确认）

本方案把**发送端**定在「**部署机器本机上启动的 Chromium**」，即现有 `channel='server'`（看板上的「通道：服务器浏览器」）。

| 「本地浏览器」指 | 结论 |
|---|---|
| **部署机器上本机跑的浏览器**（服务端发送） | ✅ **已确认走这条**，登录态入库成立，按本文实现 |
| **用户自己电脑的浏览器**（方案C 扩展，发送也在本机） | 登录态入库**没有意义**（扩展本机已有 cookie）。该形态由**方案C**覆盖：用本机浏览器通道发送，登录态不出本机 |
| **两者都要** | 本仓库**两者并存**：服务器通道读数据库（本文）；本机通道由扩展在本机发送（方案C）。两条链路独立，互不影响 |

> 补充：方案 B 下，「登录」这一步即使最终用于服务器发送，也**发生在用户本机浏览器**；服务器只接收加密后的登录态。

# 附：如果不入库，只把文件放共享存储（备选）

| 方案 | 优点 | 缺点 |
|---|---|---|
| 登录态入数据库（本文） | 与业务数据同备份、可观测、可多实例 | 需加密与密钥管理 |
| 登录态放共享卷 / 对象存储 | 改动更小 | 多实例并发写有覆盖风险；备份链路仍分离；可观测性差 |
| 现状（本地文件） | 零改动 | 容器重建即丢，不可扩容 |

> 结论：**入库是三个选项里最稳的**，代价是要认真做加密与密钥管理。

# 9 用户视角：发送过程能看到什么（服务端发送）

## 结论

**默认看不到聊天窗口。** 用户在网页上看到的是**看板顶部的进度面板**，不是 1688 的聊天弹框。

## 用户实际看到的内容

| 位置 | 内容 |
|---|---|
| 进度条 | 「发送催收消息：3/12 · 当前: XX公司 · 成功2 失败0 · 已用45秒 · 约剩3分」 |
| 实时日志 | 最近 40 条：`✓ 浏览器已启动` / `✓ 某公司 发送成功 (3条消息, 18s) · 催收次数 +1` / `✗ 某公司 …失败原因` |
| 历史核对 | 发送结束后在「催收次数」里查：时间 / 结果 / 金额 / 订单号 / 失败原因（`send_log`） |

## 为什么看不到

| 原因 | 说明 |
|---|---|
| 浏览器不在用户电脑上 | 它跑在**部署机器**上，用户本机没有任何窗口 |
| 云服务器自动无头 | Linux 无 `DISPLAY` → `lib/browser.js#resolveHeadless()` 自动切**无头**，连服务器桌面都没有窗口 |
| 本地部署也看不到 | Windows/macOS 部署时是有头的，但那是**服务器那台机器的桌面**，远程用户依旧看不到 |

## 三种「让用户看到」的做法

| 做法 | 效果 | 成本 | 结论 |
|---|---|---|---|
| 进度面板（**已采用**） | 进度 / 日志 / 历史 | 0 | **保留** |
| 逐家**截图存档** | 每发完一家存 1~2 张关键截图，可留证 | 低 | 未采纳 |
| **实时投屏** | 用户实时看到服务器浏览器画面 | 高：每路一条 JPEG 流，并发时 CPU/带宽明显，且拖慢发送 | **未采纳**（投屏能力已随方案 B 一并移除） |

## 判断依据

催收是**批量任务**，用户不需要操作那个窗口，真正要的是「**发成功几家 / 哪家失败 / 发了什么内容**」。所以：

- 进度面板已经覆盖前两项，**再补截图只是可选**；
- 实时投屏成本高一个量级，且与「服务器不承载登录画面」的安全取向相冲突 —— 方案 B 已把 `lib/live-browser.js`（CDP 投屏 + 输入回灌）**整块删除**。

> **已定（2026-10-13）**：发送过程**只要进度面板**；不做逐家截图；**不做实时投屏**；登录也不投屏（见 §10.6）。

# 10 登录方式与安全：投屏登录 vs 本地登录后上传登录态

## 10.0 已决定：方案 B（本地登录上传，彻底去掉投屏登录）

2026-10-13 定稿：**采用方案 B**。服务器不再承载任何登录画面，登录只在用户本机浏览器发生。

## 10.1 被否方案：投屏登录 = 「在服务器上登录」

服务器起一个 Chromium → 打开 1688 登录页 → CDP `Page.startScreencast` 把画面推到网页 → 用户的鼠标/键盘事件经 WS 回灌到服务器浏览器（`Input.dispatchMouseEvent / KeyEvent`）→ 登录完成后 `storageState()` 存盘。

**这套实现已删除**（`lib/live-browser.js` + `/api/browser/*` + `WS /ws/browser` + 看板直播弹窗）。

## 10.2 安全代价（诚实评估）

| 风险 | 说明 | 严重度 |
|---|---|---|
| 密码可能过服务器 | 用户若**输账号密码**，凭据经「用户浏览器 → 服务器 → 服务器 Chromium」；服务器在那一刻能接触到它（扫码则密码不过） | 高 |
| 登录态必然落在服务器 | 扫码确认的是「**服务器这台设备**」登录了 1688（手机只是确认）。cookie 落在服务器 | 高 |
| 服务器 = 账号集合体 | 服务器被攻破 / 内部人员作恶 → 一次性拿到**所有用户**的 1688 会话，等于能操作全部账号 | 高 |
| 风控 / 异地登录 | 大量用户从**同一个服务器 IP** 登录，易触发 1688 异地登录提醒、验证码 | 中 |
| 投屏流本身 | WSS 加密，但画面含登录二维码/账号信息，须保证无第三方可读 | 低-中 |

## 10.3 采用的方案：本地登录 → 把登录态交给服务器（已实现）

**已落地**，逐条对应实现位置：

| 步骤 | 做法 | 实现位置 |
|---|---|---|
| 1 用户在本机登录 | 在自己习惯的浏览器登录 1688（往往**已登录**，无需重复登录） | — |
| 2 扩展抓取 | `chrome.cookies.getAll({domain:'1688.com'})` 取 cookie（含 httpOnly，`sameSite` 映射 `None/Lax/Strict`、`expirationDate`→`expires`、会话 cookie→`-1`）+ `chrome.scripting.executeScript` 从已打开的 1688 标签页取 `localStorage` 作为 `origins` | `extension/background.js` |
| 3 上传 | 用看板生成的**一次性上传码**（6 位、10 分钟、用后即焚）POST 到 `{serverUrl}/api/state/upload`，走 HTTPS | `server.js` + `extension/popup.js` |
| 4 入库 | 服务器 AES-256-GCM 加密 → UPSERT `login_state`（**与需求① 天然合并**） | `lib/state-store.js` |
| 5 发送 | 服务端本机 Chromium `launch({ storageState })` 发送（成功 `touch`、失效 `markExpired`） | `lib/browser.js` + `server.js#doSend` |

> 改动很小：现有 `extension/manifest.json` 原本已有 `storage / tabs / alarms` 与 `*://*.1688.com/*` host 权限，**补 `cookies` + `scripting`** 两个权限，再挂一个「上传登录态」区块即可。

## 10.4 三种登录方式对比

| 维度 | ~~投屏登录~~（已删除） | **本地登录 + 上传态（已采用）** | 本机浏览器通道（方案C，并存） |
|---|---|---|---|
| 密码是否经过服务器 | 输密码时**会**（扫码不会） | **不会** | 不会 |
| 登录态是否落在服务器 | **是**（文件） | **是**（加密库） | **否**（不出本机） |
| 用户体验 | 要在网页里扫码/输入 | 最自然（本机已登录，点一下即传） | 自然，但要装扩展并保持开着 |
| 1688 风控 | 差（服务器 IP 集中登录） | 好（本机真实 IP） | 好 |
| 服务器额外负担 | 每登录用户一路投屏 | 无（只收一份 JSON） | 无 |
| 额外依赖 | 无 | 扩展（一次性安装） | 扩展 + 保持浏览器开着 |

## 10.5 结论

1. **投屏登录已按方案 B 彻底移除**；服务器不再承载任何登录画面。
2. **本地登录 + 上传登录态**采用为唯一登录方式：安全（密码不过服务器）+ 体验（不用重复登录）+ 风控（本机 IP）三赢。
3. **边界必须说清**：只要坚持**服务端发送**，登录态就**必然**在服务器上——加密只是把它变成「泄库 **且** 泄密钥」两把锁。
   - 若「登录态绝不落服务器」是硬要求 → 走**方案C**（用户自带浏览器发送，态不出本机；本仓库同样支持，见 `docs/方案C_用户自带浏览器.md`）。
4. 本次改动是**一条链**：写入来源一个（扩展上传）+ 一个迁移来源（历史文件），**读取只有一个**（发送时读库）。

## 10.6 登录方式的三种落法与最终选择

| 落法 | 说明 | 结果 |
|---|---|---|
| A | 本地登录上传为主，投屏登录**保留为兜底** | 未采纳 |
| **B** | **彻底去掉投屏登录，只留本地登录上传（服务器不再承载登录画面）** | ✅ **已采用并实现** |
| C | 维持投屏登录为主，本地登录上传作为**可选加速** | 未采纳 |

**方案 B 的收益（已在代码中消除的风险）**：服务器不接触 1688 密码；无投屏流，无并发带宽/CPU 开销；登录走用户真实 IP，风控更友好；投屏相关代码（`lib/live-browser.js`、`/api/browser/*`、`WS /ws/browser`、看板直播弹窗）整块删除，攻击面变小。
