## 1. 业务背景

1688 采购方（买家）每月在平台大量采购，但平台不强制卖家在时限内开票。买家需人工逐个联系卖家催收发票，沟通成本极高（本项目使用者约 12143 单交易成功订单、2756 家卖家）。

本项目现在做两件事：

1. **数据归集与统计**：把 1688 导出订单 + 电子税务局导出全量发票统一入库 MySQL，通过「销方名称 ↔ 商家名称」映射表把两边的商家对上，看板按商家统计订单额、已开票额、待开票额
2. **催收消息**：对存在待开票金额的卖家，通过旺旺聊天自动发送催收消息（每家 3 条：模板含总金额与抬头、订单清单、固定提醒）。**消息只在用户本机浏览器里发出**（扩展驱动 1688 聊天页），服务器不接触登录态

**已下线**：批量提交开票申请（`/api/apply`、`doApply`、看板「提交申请」按钮、行内「提交申请」按钮）；服务器浏览器发送（`doSend`、`lib/state-store.js`、登录态上传 `/api/state/*`）。

**业务红线**：只催收真实交易对应的发票，绝不涉及虚开。

## 5. 数据库结构（库名 invoice_bot）

### 5.1 `invoice_order` — 1688 完成订单表
来源 `data/完成订单/*.xlsx`。主键 `order_no`（订单编号，多 SKU 续行已按主行去重）。关键字段：

| 字段 | 说明 |
|---|---|
| `seller_company` / `seller_login` | 卖家公司名 / 会员名（登录ID，发消息的 touid 来源） |
| `pay_amount` | 实付款，金额统计口径 |
| `pay_time` / `created_at` | 订单付款/创建时间（Excel 序列号已转本地时间字符串） |
| `invoice_state` | `ENUM('none','applying','issued')` 订单级**有效**开票状态 |
| `state_source` | `ENUM('platform','manual')` 状态来源：platform=快照同步，manual=**人工确认已开票**（商家线下开票）。快照同步与重新导入都不得覆盖 manual 行 |
| `state_updated_at` / `state_note` | 状态时间 / 备注（人工确认时写入「人工确认已开票（商家线下开票）」） |
| `source_file` / `imported_at` | 溯源字段 |

### 5.2 `issued_invoice` — 历史已开票数据表
来源 `data/已开票订单/*.xlsx`（电子税务局「全量发票查询」导出）。**一行 = 一张发票的一个明细行**，数电票以 `e_invoice_no` 标识发票。

- `seller_name` 税务局口径销方名称；`seller_company` 是**映射后**的 1688 商家名称（统计用）
- `row_hash` CHAR(40) = md5(`e_invoice_no|发票代码|货物名称|规格|单位|数量|金额|税额|销方名称`)，唯一键去重
- 只导入「信息汇总表」这个 sheet（明细行）；没有该 sheet 时退化为第一个 sheet；自动跳过序号为「合计行」的行。**不要同时导入「发票基础信息」**，那是按发票汇总的，会重复计数

### 5.3 `seller_name_mapping` — 名称映射表
`tax_seller_name`（税务局销方名称，唯一键）→ `seller_company` / `seller_login`。
`match_type` = auto/manual/**ignored**，`match_rule` = exact/normalized/contains/login/remark，`is_confirmed` 标记是否人工确认。
`is_ignored` = 1 表示**人工确认该销方名称没有对应的 1688 商家**：不出现在待比对列表、不参与自动匹配（`autoMapSellers` 会跳过）、`issued_invoice.seller_company` 回填为 NULL、不计入「未匹配销方名称」计数；名称映射页「已忽略」区可随时恢复（恢复时若记录无真实映射则直接删除该行）。

### 5.4 `send_log` — 催收发送记录
替代原 `data/sent-log.json`。**一行 = 一次发送尝试**（旧版按天合并的唯一键已移除），`result` 区分 `ok`/`fail`。看板据此统计：
- `催收次数` = **`SUM(result='ok')`，只计成功**（失败尝试不计入次数）
- `最近催收时间` = `MAX(CASE WHEN result='ok' THEN sent_at END)`，即**最近一次成功**催收（失败不算）
- `sendFailCount` = `SUM(result<>'ok')`，仅作展示（悬浮徽章 / 明细里可见「失败」），不影响催收次数
- `channel` 区分入口（web=看板 / cli=命令行 / legacy=旧 JSON 迁移）；CLI 断点续发只认 `result='ok'` 的记录
- **`amount` / `order_nos`（2026-10-12 新增）**：发送当时的待开票总金额与订单号清单（多个用「；」分隔）快照，供看板点「催收次数」弹窗查看历史。web/cli 两条发送链路都会写入；2026-10-12 之前的老记录为 NULL，弹窗显示「—」
- **`error`（2026-10-12 新增）**：失败原因摘要（仅 `result='fail'` 写入，取错误首行、截断 250 字；成功行恒为 NULL）。web（`doSend` 捕获的 `e.message`）与 cli（`send-messages.js`）均写入，供弹窗与展开明细排查「为什么发失败」。老记录为 NULL
- 旧版 `data/sent-log.json` 会在 `send_log` 为空时由 `migrateLegacySentLog()` 自动迁入一次（时刻统一记 12:00:00）；该文件已于 2026-10-10 归档到 `data/backups/legacy-cleanup-2026-10-10/`

### 5.5 `import_log` — 导入日志
每次导入按文件记一行（总行数/写入/跳过/自动匹配数/未匹配数/状态），排查「数据为什么没更新」。**2026-10-13 起 `skipped` 列的含义变为「按订单号/行哈希去重后跳过的已有行数」**（增量导入）。

### 5.6 `v_unmatched_seller_name` 视图
`issued_invoice LEFT JOIN seller_name_mapping … WHERE m.id IS NULL`（join 条件含 `is_ignored=1 OR seller_company IS NOT NULL`），即**同时排除「已映射」与「已忽略」**两类，按销方名称聚合出行数/金额/首末开票日期/税号/备注。「名称映射」页的待人工比对清单与看板「未匹配销方名称」计数都来自它。

### 5.7 `login_state` — **已废弃（2026-10-13 删除）**
原「1688 登录态加密入库」表（AES-256-GCM，`lib/state-store.js`，`/api/state/*` 四个接口，扩展「上传登录态」）**已整表废除**：服务器不再保存任何登录态，`sql/schema.sql` 中该 DDL 已注释、`db.js ensureSchema()` 不再建表。历史数据行留在库里无副作用（无代码引用）；如需彻底清理可 `DROP TABLE login_state`（操作前先备份）。**发送通道只剩方案C 本机浏览器通道，见 §5.8。**

### 5.8 `app_user` / `agent_task`（多租户 + 本机发送通道）
- **`app_user`**：账号表。`username` 唯一 —— **口径：登录账号 = 公司全称**（允许中文，见 §10-23）；`password_hash`（scrypt）、`role`（`admin`/`user`）、开票抬头 `company_name` / `tax_no` / `email`（催收话术的 `{companyName}/{taxNo}/{email}` 按账号取值，**仅超级管理员**在「系统管理 → 用户管理」维护，见 §10-24）、`token_version`（改密/禁用即时作废旧会话）、`status` 启用/禁用。业务表全部带 `user_id` 外键实现数据隔离。
  - **超级管理员（admin）是纯系统账号**：不承载看板数据、不落开票抬头（`createUser`/`updateUser` 对 `role=admin` 强制清空抬头三列）；用户列表里 admin 行**只有「重置密码」**，没有「查看数据 / 编辑」。业务数据归业务账号（如「中山仕赫贸易有限公司」）。
- **`agent_task`**：本机浏览器通道的发送任务（**当前唯一发送通道**）。`items` JSON 保留每条 `{loginId,company,amount,orderNos,status}`（`pending|ok|fail`）用于**断线续跑**；`resume_of` 指向被接续的来源任务（NULL=全新任务）。状态机 `queued → running → done | aborted | failed`。
  - **`task_progress` 推送（2026-10-13 新增）**：服务器在任务开始、每完成一家、任务结束时经 `agentHub.send` 向扩展推 `{type:'task_progress', taskId, total, done, ok, fail, current, finished, sellers}`，扩展 `background.js` 存 `state.task`，`popup.js` 渲染实时监控面板（进度条 / 当前卖家 / ok·fail·pending / 每家状态点）。
  - **`client_stop`（2026-10-13 新增）**：扩展弹窗点「停止」→ `background.js` 发 `{type:'client_stop', taskId}` → 服务器置 `ctx.taskState.stopRequested = true`（当前家发完即停，等待间隔时立即停）。

## 6. 导入与自动匹配逻辑（import-to-db.js）

**导入策略：增量去重（2026-10-13 起，原「全量重建」已废除）。** 不再 `DELETE FROM invoice_order / issued_invoice`，改为：

- `importOrders`：按 `order_no` 建 Map 去重 → 查库已有 `order_no` 集合 → **只 `bulkInsert` 新行**（已有行跳过并计入 `skippedExisting`）；新行 `invoice_state='none'` / `state_source='platform'`，随后由 `applyInvoiceStatus` / 人工确认维护
- `importInvoices`：按 `row_hash` 去重（`uk_user_row_hash`），只插新行；随后执行**映射回填 JOIN UPDATE**：
  ```sql
  UPDATE issued_invoice i JOIN seller_name_mapping m
     ON m.user_id = i.user_id AND m.tax_seller_name = i.seller_name AND m.seller_company IS NOT NULL
   SET i.seller_company = m.seller_company
   WHERE i.user_id = ? AND (i.seller_company IS NULL OR i.seller_company <> m.seller_company)
  ```
  —— 增量模型下，**后建的映射要能作用到老行**，否则老发票行永远统计不上
- **行为变化（须知）**：从文件夹里**删掉**某个 Excel 后，对应数据**不会**从看板消失（只增不删）。要真正清数据只能删库/删行
- `seller_name_mapping` 从不删除，保护人工维护成果；`state_source='manual'` 的人工确认不受导入影响

**统计口径（server.js，看板唯一真相）：**

- **两级聚合**：`loadSellers()` 产出**会员名级**行；`loadCompanies()` 在其上做**公司级**聚合（`/api/data` 返回 `companies[]`，会员名在 `companies[].members[]` 子树）。看板一行 = 一家公司，会员名在子树里
- 已开票金额 = `issued_invoice` 按**映射后 seller_company** 聚合的 `SUM(total_amount)`（税务局「价税合计」明细总和）
- 已开票数量 = `COUNT(DISTINCT 数电票号/发票号/row_hash)`（税务局**发票张数**）。⚠️ 税务局导出是「一张票多个货物各占一行、共用同一数电票号」，去重后一张票只计 1 张，所以**张数 ≤ 明细行数**（属预期，非重复计数 bug）。另返回 `invoiceRowCount = COUNT(*)` 供前端在 tooltip / 明细段头展示「X 行货物明细」对照
- 待开票金额 = `max(订单 SUM(pay_amount) − 已开票金额, 0)`。**公司级按公司总额重算**（不用各会员名 max 后求和，避免截断误差）
- **催收按钮（会员名级）/「有待开票」筛选（公司级）的判定 = `unissuedCount > 0`**：人工把订单全部确认后按钮自动置灰，避免点了空发（服务端本就会跳过无可催收订单的卖家）
- 催收次数 / 最近催收时间 = `send_log` 按 `seller_login` 聚合（**只计 `result='ok'`**）；公司行 = 各会员名求和 / 取 MAX
- 同一公司多店铺：发票额只挂「主行」（优先映射表登记的会员名，否则订单数最多的行），其余行标注归属，**避免重复计入**。公司级聚合时非主行本来就是 0，求和后正好等于公司口径
- **前端筛选/勾选的粒度**：筛选与列表行 = 公司；勾选与发送 = 会员名。公司复选框会一次带出该公司全部可催收会员名
- **看板筛选（2026-10-12 第二次改版）**：标签「未催收（从未）」已移除（只剩无实际过滤作用的「全部」，因为筛选已由下拉接管）；下拉与搜索框**任意组合（AND）**——
  `催收状态`：**已催收**（默认，`sendCount > 0`，即有成功催收记录）/ **最近 N 天未催收**（`lastSentAt` 为空或距今 ≥ N 天，N = 7/15/30/90；原「不限」选项已按需求改为「已催收」）；
  `开票状态`：已开票 = `pendingAmount == 0`，未开票 = `pendingAmount > 0`；
  搜索：公司名 ∪ 会员名(loginId)。「有待开票 / 有开票记录 / 人工确认」旧标签均已移除（对应数据仍展示在列里）
- **看板排序（2026-10-12 改版）**：`visibleCompanies()` 里对过滤结果重排——**最近催收时间倒序**（`lastSentAt` 转毫秒，无催收 = 0 沉底）→ 催收时间相同（含都无）再按**待开票金额倒序**。后端 `/api/data` 仍按待开票金额排序返回（发送任务遍历与顺序无关），展示顺序以前端为准
- **全选范围（2026-10-12 改版）**：「全选当前页」只勾选**当前分页**公司的可催收会员名（`pageOf('dash').slice(visibleCompanies())`），不再跨页全选

**催收口径（会员名级，`server.js doClientSend`）：**

- `{amount}` = 该会员名的待开票金额（看板会员名子树里的「待开票金额」）
- `{orderId}` = 该会员名除「已开票」外的全部订单号：`detail.orders.filter(o => o.invoice_state !== 'issued')`（平台已开票 + 人工确认的都排除）
- 聊天 touid 依赖会员名（`seller.sellerLogin`），所以发送天然是会员名粒度；同公司多店铺各自收到自己店的账

**订单开票状态 `invoice_order.invoice_state`（none/applying/issued）来源链路：**

1. `applyInvoiceStatus()`（`import-to-db.js`，导入时自动执行）：读取 `data/users/<id>/invoice-status.json` 快照，`UPDATE ... WHERE order_no IN (...) AND invoice_state <> 'issued' AND state_source <> 'manual'`（已开票不回退、人工确认不覆盖）。**快照文件不存在时静默跳过**（订单保持 `none`）
2. 人工确认（`state_source='manual'`）由 `/api/order-state` 写入，优先级最高；「取消人工确认」按 `invoice-status.json` 快照逐单回推平台真实状态
3. 原 `refresh-status.js`（Playwright + mtop 自动拉快照）**已随服务端浏览器一同删除**；需要平台状态时由用户手动放置快照文件，格式不变

**名称自动匹配**（`matchSeller`，按顺序命中即返回；同公司多会员名时用 `pickAmongSiblings()` 消歧：①发票备注店铺名线索 → ②订单数最多，保证可复现）：

1. `exact` — 销方名称规范化后与 `seller_company` 完全相同（多会员名消歧后，纯按订单数定的标 `is_confirmed=0` 待复核）
2. `login` — 与卖家会员名完全相同
3. `contains` — 两边规范化后互相包含，且较短一方 ≥4 字、占较长一方 ≥50%（防误判）；命中标记为**待人工复核**（`is_confirmed=0`）
4. `login`（包含）— 销方名称包含卖家会员名
5. `remark` — 发票备注里出现商家名/会员名，或 `1688 XXX` 形式的店铺名线索

匹配不上的名称**不写占位行**，由视图 `v_unmatched_seller_name` 暴露，等人工在「名称映射」页补。再次导入时已映射的名称不再重新匹配。

**名称规范化** `normName()`：去空白（含全角空格）、全半角括号统一、去 `，、;·.-_*` 等标点、转大写。

## 8. 聊天发送核心逻辑（本机浏览器通道）

**服务端 `sendToSeller`（Playwright）已退役**，仅作为选择器与等待逻辑的参考保留在 `lib/sender.js`。当前唯一发送实现在**用户本机浏览器的扩展**里：

- `extension/content.js`：在 1688 聊天页（`air.1688.com/app/ocms-fusion-components-1688/def_cbu_web_im/index.html?touid=cnalichn{卖家登录ID}&siteid=cnalichn&status=1`）逐家发送，键盘模拟逻辑与参考实现一致：
  1. `openChatReady`：打开 URL + `bringToFront()` → 轮询等 `def_cbu_web_im_core` iframe 内 `pre.edit[contenteditable="true"]` 出现（找到后 1.6s 再确认一次防 iframe 重建；总等待≥2.5s；单轮 15s 未就绪则 reload，最多 3 轮）。**每次操作前必须重新 getFrame**
  2. `ensureContact`：判定右侧空状态文案消失（轮询，最多 8s）；未自动选中则点击左侧会话列表目标项（兜底，不拦截）
  3. `sendMessage`（每条）：清残留草稿（Ctrl+A+Delete）→ `insertText` 整体插入 → 轮询验证编辑器有内容 → 点 `button.send-btn` → **轮询验证消息尾部30字出现在聊天记录 `pre.edit` 里**（成功判据）；失败重试 1 次
  4. 消息之间随机停 1.2~2.5 秒（**仅非最后一条**；最后一条发完即关页）
- `extension/background.js`：WS 客户端（配对码注册 / 心跳 20s）、收 `send_batch` → 开工作标签页跑 `runBatch` → 每完成一家回 `sent`；维护 `state.currentCompany` / `state.task`；响应 `STOP_TASK`（弹窗停止按钮）发 `client_stop`
- `server.js`：`doClientSend(tenantId, loginIds)` 建 `agent_task` + `CLIENT_TASKS` ctx → 经 `agentHub.send` 下发；`onAgentSent` 更新 items 状态并写 `send_log`（result=ok/fail + amount/order_nos/error 快照）；`finishClientTask` 收尾；三处都调 `pushClientProgress` 推 `task_progress`

**性能参考（2026-10-12 服务端实测）**：等待全部改为「条件满足即继续」的轮询后，单家发送动作约 10~15s（原固定盲等约 45s，A/B 实测 34.4s → 6.6s，5.2x）。家与家之间的 `sendGapMinSec/MaxSec`（默认 15~30s）是防限流主开关，不在 sender 内，可在看板设置页调整。本机通道沿用同一组参数。

**健壮性（继承自服务端实现，2026-10-12）**：
- `getFrame/getEditor` 全部容错——iframe 重建瞬间的 detached 异常视为「未就绪」继续轮询，不再让单家整批失败
- **登录态失效快速失败**：就绪等待期间若 URL 跳回 `login.1688.com`，立刻抛「登录态失效」并中止整批（不写 send_log，避免污染统计与空转）
- 就绪等待有上限（3 轮 ×15s，最多 reload 2 次），卡死的卖家约 45s 后跳过，不会无限等待
- **家间间隔可中断**：等待期间分段轮询停止标志，点「停止」在等待期间即时生效（不必干等整个间隔）
- **断线续跑**：`agent_task.items` 逐条状态机 + `/api/agent/resumable` + `/api/agent/resume`，只补发 `pending/failed`，**已成功的绝不重发**；服务器重启也会把 running 任务标记中断

## 10. 历史踩坑（改代码前必读）

1. **消息逐行炸开**：1688 聊天把多行文本按行拆成多条消息（insertText 也一样）→ 订单清单必须单行「；」分隔，超 450 字再起一条
2. **服务器发送失败三天**：doSend 构造 msgSeller 漏传 `loginId` → touid=undefined → 联系人永不选中。**教训：跨层传参必须断言关键字段**
3. **「AI询盘」推广弹窗**会整层盖住聊天界面且时机随机 → 每次 sendMessage 前点按钮清理（点不掉时 remove `.ant-modal-wrap` DOM）
4. **验证码/滑块**出现时须暂停等人（lib/browser.js 的 waitHuman），不要死循环重试
5. Playwright 1.64 无 `page.waitForTimeout`，用本地 `sleep`
6. curl 传中文 JSON 会乱码，测试须 `--data-binary @file` 或 Node 侧请求
7. **server.js 改完必须重启进程**（改代码不重启 = 没生效）
8. **MySQL 未启动时 server 启动不报错**，只是 `/api/data` 返回 500。`server.listen` 回调里已做 ping 自检并打印提示
9. **`mysql2` 默认 dateStrings=false 会因时区把 DATETIME 漂移**，`db.js` 已统一 `dateStrings:true` + `decimalNumbers:true`
10. **库名无法参数化**，`db.safeDbName()` 用白名单正则校验，拼接前必过
11. **Excel 日期是 1900 序列号**，用 `XLSX.SSF.parse_date_code()` 转**本地时间**再格式化；不要用 `(n-25569)*86400*1000`（会差一个时区）
12. **发票导出有两个 sheet**，只能导「信息汇总表」，导「发票基础信息」会与明细重复计数
13. **导入日志字段 NOT NULL 默认值**：`inserted/skipped/auto_mapped/unmatched` 不传会触发 `Column 'auto_mapped' cannot be null`，`logImport()` 已做 0 兜底
14. **CLI 与看板的发送记录必须同源**：看板「已催收」读 `send_log` 表，`send-messages.js` 早期只写 `sent-log.json` → 命令行发的记录看板看不到。现已统一读写 `send_log`（`send-messages.js` 本身已于 2026-10-13 删除）
15. **`send-messages.js` 已依赖数据库**：发送前读 `send_log` 做断点续发判定，DB 未启动会直接报错（catch 里已给启动提示）；`--dry-run` 不碰数据库，可离线预演
16. **老库升级走 `db.migrate()`**：`ensureSchema()` 执行 schema.sql（CREATE IF NOT EXISTS 不会改老表）后，用 information_schema 判断列/索引是否存在再 ALTER，幂等可重复执行。新增列必须同时改 schema.sql **和** migrate()
17. **人工确认状态要「三层防覆盖」**：① `applyInvoiceStatus` 的 UPDATE 带 `state_source <> 'manual'`；② `importOrders` 回填 `state_source/state_note`（增量导入下新行无旧状态可回填，靠①③ 保护）；③ 取消确认时按 `invoice-status.json` 回推平台状态，而不是粗暴置 none
18. **send_log 改为事件日志后**：`INSERT` 不能再带 `ON DUPLICATE KEY UPDATE`（唯一键已删）；CLI 断点续发只认 `result='ok'`，否则失败记录会永久跳过该卖家
19. **`const [rows] = await q(...)` 多解构一层（2026-10-13 踩）**：`db.js` 里的 `q()` 助手**已经返回行数组**，写成 `const [atRows] = await q(...)` 后又解构一次 → `atRows` 是**第一行对象**，`atRows[0]` 恒为 `undefined` → 分支永远走「建表」、`else`/补列分支形同虚设。因为 `CREATE TABLE IF NOT EXISTS` 不报错，**隐蔽性极高**。新代码一律用 `tableExists/colExists` 助手，别手写 information_schema 查询再解构
20. **`schema.sql` 顶部硬编码库名（2026-10-13 踩）**：文件里写了 ``CREATE DATABASE \`invoice_bot\` `` + ``USE \`invoice_bot\` ``，导致 `MYSQL_DATABASE` / `config.database` 形同虚设 —— **换库/测试库会误写进生产库**。`db.js` 已改为读文件时按目标库名改写，新增 DDL 不要再写库名
21. **新增敏感数据入表要加密 + 密钥外置**（历史经验，随 login_state 废除已不适用，留作方法论）：任何「入库的凭据类数据」都要加密 + 密钥外置；**2026-10-13 的最终解法更彻底——登录态根本不入服务器**，从源头消灭了这类风险面
22. **扩展上传接口必须放在登录闸门之前**（历史经验，`/api/state/upload` 已删除，留作方法论）：用一次性码鉴权的扩展接口若被 `/api/*` 登录校验拦住会 401；且要**先校验请求形状再消耗码**，否则一个空请求就能把码烧掉
23. **「登录账号 = 公司全称」必须放开用户名的中文限制（2026-10-13 踩）**：`validUsername` 原为 `/^[A-Za-z0-9_.-]{4,64}$/`，**中文公司全称会被直接拒绝**——而业务口径就是把开票抬头的公司全称当登录账号。现改为 `/^[\u4e00-\u9fa5A-Za-z0-9_.·()（）-]{2,64}$/`；配套：`createUser` 未传 `username` 时取 `companyName` 兜底，`updateUser` 支持改 `username`（唯一性校验 + `admin` 锁死不许改名），看板「新增用户」把两个字段合成一个输入框
24. **开票抬头是「用户信息」，不能放全局配置区（2026-10-13 调整）**：抬头一度同时存在于 `config.json.buyerInfo` 和「系统管理 → 我的开票抬头」卡片（改的是当前登录者自己）→ 语义混乱。现在**唯一来源是 `app_user.company_name / tax_no / email`**，只在「系统管理 → 用户管理 → 编辑」里按账号维护。`/api/config` 的 `buyerInfo` 字段保留但**仅作向后兼容**（看板已不再提交它）；发送话术渲染前统一由 `buyerInfoOf(userId)` 注入覆盖
25. **删用户 `purge:true` 是「连根拔」，测试脚本绝不能与真实业务账号重名（2026-10-13 踩，已靠迁移前备份恢复）**：`/api/admin/users/delete` 带 `purge` 会 `DELETE` 该用户在 6 张业务表里的全部数据 + `rm -rf data/users/<id>/`（Excel / 登录态文件一并删）。`tmp-user-model-check.js` 曾把测试公司名写成真实的「中山仕赫贸易有限公司」，先删同名用户再重建 → **已迁移到该账号的数据全部被清**。已加双保险：测试改用假名「测试公司甲有限公司」+ 运行前检测「同名且持有业务数据」直接中止 + 结束后自清理
26. **迁库必须连文件一起搬（2026-10-13 踩）**：启动时的 `migrateLegacyData(adminId)` 是「**文件存在 且 库里没有**」才动作、逐用户独立幂等。只把 `user_id` 改掉而不搬走 `data/users/<旧id>/` 下的遗留文件、根目录 `data/完成订单` 等，**下次重启就会把数据原样灌回 admin**。正确做法：DB 迁移 + 文件搬迁 + 删除根目录遗留件，三步缺一不可
27. **同文件多 Edit 不能放在一条消息里并行发（2026-10-13 踩）**：对同一文件连续发多个 Edit 工具调用时，后发的编辑可能**静默丢失**（基于过期内容匹配）。改大文件要么**逐条串行 Edit**，要么**整文件 Write**；改完必须 grep 关键锚点复核
28. **增量导入的去重口径要在代码里查库，不能靠唯一键（2026-10-13 设计）**：`invoice_order` **没有** `order_no` 唯一键（多 SKU 场景历史上按主行去重），增量导入只能「先 `SELECT order_no` 查出已有集合 → 内存 Map 过滤」；`issued_invoice` 有 `uk_user_row_hash`，但同样按集合过滤而非依赖 INSERT IGNORE（要在返回值里区分 `inserted/skippedExisting` 给用户看）
29. **增量模型下映射回填必须做 JOIN UPDATE（2026-10-13 设计）**：全量重建时代码里就地匹配；增量导入只碰新行，**后建的名称映射对老发票行不生效**，必须显式 `UPDATE issued_invoice i JOIN seller_name_mapping m ...` 回填，否则老行永远统计不上

## 11. 已知设计取舍

- **提交申请彻底移除**：`/api/apply` 返回 410；订单级「已申请」状态只能靠用户放置 `invoice-status.json` 快照同步
- **发送通道只剩本机浏览器（2026-10-13 定，方案C）**：登录与发送都在**用户自己电脑的浏览器**里完成（扩展 + 配对码），服务器**不保存登录态、不启动任何浏览器**。取舍：密码与登录态都不过服务器，泄库也拿不到 1688 账号；代价是发送依赖用户浏览器开着、关掉会中断（用断线续跑缓解），且仅支持桌面 Chrome/Edge
- **服务器只编排不发送**：`doClientSend` 建 `agent_task` + 经 WS 下发；实际聊天页操作在扩展里；服务器负责状态机、`send_log` 记账、断线续跑与 `task_progress` 推送
- **发送过程只看进度面板**：不做逐家截图、不做实时投屏。批量任务用户要的是「发成功几家 / 哪家失败 / 发了什么」，看板进度面板 + 扩展弹窗监控面板 + `send_log` 历史已覆盖
- **CLI 与看板发送记录同源**（历史）：`send-messages.js` 与 `server.js` 都读写 `send_log` 表；CLI 入口已随服务端浏览器删除，当前唯一入口是看板
- **两套「已开票」口径并存**：`invoice_order.invoice_state` 是平台侧的订单级状态（含人工确认）；`issued_invoice` 是税务局导出的发票级历史数据。看板分别呈现，**不要混算**（税务局导出无订单号，无法直接关联到订单）。因此「已开票金额/张数」只来自税务局文件；人工确认只改订单状态计数，不影响金额
- **催收次数只计成功**：`send_log` 记录每次发送尝试并标 `result`；统计时 `催收次数 = SUM(result='ok')`、`最近催收时间 = 最近一次 ok 的 sent_at`，失败尝试（`SUM(result<>'ok')`）仅在明细与悬浮提示里展示，**不计入次数**
- **待开票金额 = max(订单总额 − 已开票金额, 0)**，按映射后的商家名汇总；发票额大于订单额时标记 `overInvoiced`
- **导入是增量去重（2026-10-13 起）**：只插不删，文件夹里的 Excel 不再是「唯一真相」而是「增量来源」；删除文件不会删数据，要清数据只能删库/删行；映射表与人工确认状态不受影响
- **订单数据不自动更新**：依赖用户手动导出 xlsx（API 拉全量订单会限流）
- **无并发**：发送任务串行（浏览器操作天然不可并行；一个租户同时只允许一个任务）
- **发送耗时构成**：单家 = 发送动作（约 10~15s，轮询式，见 §8）+ 家间 `runtime.sendGapMinSec/MaxSec`（默认 15~30s，**防限流主开关**，设置页可调）。看板时长估算 = 家数 ×（间隔均值 + 15s）
- **未做分页/虚拟滚动**：2744 家公司 / 2756 个会员名一次性下发聚合结果（约 1.5MB），订单明细改为按需加载；数据量再涨需要加后端分页
