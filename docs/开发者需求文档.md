## 1. 业务背景

1688 采购方（买家）每月在平台大量采购，但平台不强制卖家在时限内开票。买家需人工逐个联系卖家催收发票，沟通成本极高（本项目使用者约 12143 单交易成功订单、2756 家卖家）。

本项目现在做两件事：

1. **数据归集与统计**：把 1688 导出订单 + 电子税务局导出全量发票统一入库 MySQL，通过「销方名称 ↔ 商家名称」映射表把两边的商家对上，看板按商家统计订单额、已开票额、待开票额
2. **催收消息**：对存在待开票金额的卖家，通过旺旺聊天自动发送催收消息（每家 3 条：模板含总金额与抬头、订单清单、固定提醒）

**已下线**：批量提交开票申请（`/api/apply`、`doApply`、看板「提交申请」按钮、行内「提交申请」按钮）。

**业务红线**：只催收真实交易对应的发票，绝不涉及虚开。

## 5. 数据库结构（库名 invoice_bot）

### 5.1 `invoice_order` — 1688 完成订单表
来源 `data/完成订单/*.xlsx`。主键 `order_no`（订单编号，多 SKU 续行已按主行去重）。关键字段：

| 字段 | 说明 |
|---|---|
| `seller_company` / `seller_login` | 卖家公司名 / 会员名（登录ID，发消息的 touid 来源） |
| `pay_amount` | 实付款，金额统计口径 |
| `pay_time` / `created_at` | 订单付款/创建时间（Excel 序列号已转本地时间字符串） |
| `invoice_state` | `ENUM('none','applying','issued')` 订单级**有效**开票状态 |
| `state_source` | `ENUM('platform','manual')` 状态来源：platform=refresh-status 拉取，manual=**人工确认已开票**（商家线下开票）。平台刷新与重新导入都不得覆盖 manual 行 |
| `state_updated_at` / `state_note` | 状态时间 / 备注（人工确认时写入「人工确认已开票（商家线下开票）」） |
| `source_file` / `imported_at` | 溯源字段 |

### 5.2 `issued_invoice` — 历史已开票数据表
来源 `data/已开票订单/*.xlsx`（电子税务局「全量发票查询」导出）。**一行 = 一张发票的一个明细行**，数电票以 `e_invoice_no` 标识发票。

- `seller_name` 税务局口径销方名称；`seller_company` 是**映射后**的 1688 商家名称（统计用）
- `row_hash` CHAR(40) = md5(`e_invoice_no|发票代码|货物名称|规格|单位|数量|金额|税额|销方名称`)，唯一键去重
- 只导入「信息汇总表」这个 sheet（明细行）；没有该 sheet 时退化为第一个 sheet；自动跳过序号为「合计行」的行。**不要同时导入「发票基础信息」**，那是按发票汇总的，会重复计数

### 5.3 `seller_name_mapping` — 名称映射表
`tax_seller_name`（税务局销方名称，唯一键）→ `seller_company` / `seller_login`。
`match_type` = auto/manual/**ignored**，`match_rule` = exact/normalized/contains/login/remark，`is_confirmed` 标记是否人工确认。
`is_ignored` = 1 表示**人工确认该销方名称没有对应的 1688 商家**：不出现在待比对列表、不参与自动匹配（`autoMapSellers` 会跳过）、`issued_invoice.seller_company` 回填为 NULL、不计入「未匹配销方名称」计数；名称映射页「已忽略」区可随时恢复（恢复时若记录无真实映射则直接删除该行）。

### 5.4 `send_log` — 催收发送记录
替代原 `data/sent-log.json`。**一行 = 一次发送尝试**（旧版按天合并的唯一键已移除），`result` 区分 `ok`/`fail`。看板据此统计：
- `催收次数` = **`SUM(result='ok')`，只计成功**（失败尝试不计入次数）
- `最近催收时间` = `MAX(CASE WHEN result='ok' THEN sent_at END)`，即**最近一次成功**催收（失败不算）
- `sendFailCount` = `SUM(result<>'ok')`，仅作展示（悬浮徽章 / 明细里可见「失败」），不影响催收次数
- `channel` 区分入口（web=看板 / cli=命令行 / legacy=旧 JSON 迁移）；CLI 断点续发只认 `result='ok'` 的记录
- **`amount` / `order_nos`（2026-10-12 新增）**：发送当时的待开票总金额与订单号清单（多个用「；」分隔）快照，供看板点「催收次数」弹窗查看历史。web/cli 两条发送链路都会写入；2026-10-12 之前的老记录为 NULL，弹窗显示「—」
- **`error`（2026-10-12 新增）**：失败原因摘要（仅 `result='fail'` 写入，取错误首行、截断 250 字；成功行恒为 NULL）。web（`doSend` 捕获的 `e.message`）与 cli（`send-messages.js`）均写入，供弹窗与展开明细排查「为什么发失败」。老记录为 NULL
- 旧版 `data/sent-log.json` 会在 `send_log` 为空时由 `migrateLegacySentLog()` 自动迁入一次（时刻统一记 12:00:00）；该文件已于 2026-10-10 归档到 `data/backups/legacy-cleanup-2026-10-10/`

### 5.5 `import_log` — 导入日志
每次导入按文件记一行（总行数/写入/跳过/自动匹配数/未匹配数/状态），排查「数据为什么没更新」。

### 5.6 `v_unmatched_seller_name` 视图
`issued_invoice LEFT JOIN seller_name_mapping … WHERE m.id IS NULL`（join 条件含 `is_ignored=1 OR seller_company IS NOT NULL`），即**同时排除「已映射」与「已忽略」**两类，按销方名称聚合出行数/金额/首末开票日期/税号/备注。「名称映射」页的待人工比对清单与看板「未匹配销方名称」计数都来自它。

## 6. 导入与自动匹配逻辑（import-to-db.js）

**导入策略：全量重建。** `DELETE FROM invoice_order` / `issued_invoice` 后重新插入，以文件夹里的 Excel 为唯一真相。两个例外：

- `invoice_order.invoice_state` / `state_source` / `state_updated_at` / `state_note` 在重建前先读进内存，重建时回填（避免 refresh-status 与**人工确认**的成果被覆盖）
- `seller_name_mapping` **不删除**，保护人工维护成果

**统计口径（server.js，看板唯一真相）：**

- **两级聚合**：`loadSellers()` 产出**会员名级**行；`loadCompanies()` 在其上做**公司级**聚合（`/api/data` 返回 `companies[]`，会员名在 `companies[].members[]` 子树）。看板一行 = 一家公司，会员名在子树里
- 已开票金额 = `issued_invoice` 按**映射后 seller_company** 聚合的 `SUM(total_amount)`（税务局「价税合计」明细总和）
- 已开票数量 = `COUNT(DISTINCT 数电票号/发票号/row_hash)`（税务局**发票张数**）。⚠️ 税务局导出是「一张票多个货物各占一行、共用同一数电票号」，去重后一张票只计 1 张，所以**张数 ≤ 明细行数**（属预期，非重复计数 bug）。另返回 `invoiceRowCount = COUNT(*)` 供前端在 tooltip / 明细段头展示「X 行货物明细」对照
- 待开票金额 = `max(订单 SUM(pay_amount) − 已开票金额, 0)`。**公司级按公司总额重算**（不用各会员名 max 后求和，避免截断误差）
- **催收按钮（会员名级）/「有待开票」筛选（公司级）的判定 = `unissuedCount > 0`**：人工把订单全部确认后按钮自动置灰，避免点了空发（服务端本就会跳过无可催收订单的卖家）
- 催收次数 / 最近催收时间 = `send_log` 按 `seller_login` 聚合（**只计 `result='ok'`**）；公司行 = 各会员名求和 / 取 MAX
- 同一公司多店铺：发票额只挂「主行」（优先映射表登记的会员名，否则订单数最多的行），其余行标注归属，**避免重复计入**。公司级聚合时非主行本来就是 0，求和后正好等于公司口径
- **前端筛选/勾选的粒度**：筛选与列表行 = 公司；勾选与发送 = 会员名。公司复选框会一次带出该公司全部可催收会员名
- **看板筛选（2026-10-12 第二次改版）**：标签「未催收（从未）」已移除（只剩无实际过滤作用的「全部」，因为筛选已由下拉接管）；下拉与搜索框**任意组合（AND）**——
  `催收状态`：**已催收**（默认，`sendCount > 0`，即有成功催收记录）/ **最近 N 天未催收**（`lastSentAt` 为空或距今 ≥ N 天，N = 7/15/30/90；原「不限」选项已按需求改为「已催收」）；
  `开票状态`：已开票 = `pendingAmount == 0`，未开票 = `pendingAmount > 0`；
  搜索：公司名 ∪ 会员名(loginId)。「有待开票 / 有开票记录 / 人工确认」旧标签均已移除（对应数据仍展示在列里）
- **看板排序（2026-10-12 改版）**：`visibleCompanies()` 里对过滤结果重排——**最近催收时间倒序**（`lastSentAt` 转毫秒，无催收 = 0 沉底）→ 催收时间相同（含都无）再按**待开票金额倒序**。后端 `/api/data` 仍按待开票金额排序返回（发送任务遍历与顺序无关），展示顺序以前端为准
- **全选范围（2026-10-12 改版）**：「全选当前页」只勾选**当前分页**公司的可催收会员名（`pageOf('dash').slice(visibleCompanies())`），不再跨页全选

**催收口径（会员名级，`server.js doSend`）：**

- `{amount}` = 该会员名的待开票金额（看板会员名子树里的「待开票金额」）
- `{orderId}` = 该会员名除「已开票」外的全部订单号：`detail.orders.filter(o => o.invoice_state !== 'issued')`（平台已开票 + 人工确认的都排除）
- 聊天 touid 依赖会员名（`seller.sellerLogin`），所以发送天然是会员名粒度；同公司多店铺各自收到自己店的账

**订单开票状态 `invoice_order.invoice_state`（none/applying/issued）来源链路：**

1. `refresh-status.js`（手动 `node refresh-status.js`）：Playwright 打开带登录态的 `buyer-invoice-list.html`，调 mtop `KsInvoicePurchaserManageMtopService.queryInvoiceApplyRecordListByPage` 分页拉两组：`bizStatusList=[1,5,6,40]`=已申请、`[2,30,31,32]`=已开票；订单号取 `orderModel.idStr`（回退 `invoiceModel.outBizId`）
2. 快照写 `data/invoice-status.json`，随后调 `applyInvoiceStatus()` 同步入库：`UPDATE ... WHERE order_no IN (...) AND invoice_state <> 'issued' AND state_source <> 'manual'`（已开票不回退、人工确认不覆盖）
3. 全量导入（`importOrders` 之后）与看板「重新导入数据」也会执行第 2 步
4. 人工确认（`state_source='manual'`）由 `/api/order-state` 写入，优先级最高；「取消人工确认」按 `invoice-status.json` 快照逐单回推平台真实状态

**名称自动匹配**（`matchSeller`，按顺序命中即返回；同公司多会员名时用 `pickAmongSiblings()` 消歧：①发票备注店铺名线索 → ②订单数最多，保证可复现）：

1. `exact` — 销方名称规范化后与 `seller_company` 完全相同（多会员名消歧后，纯按订单数定的标 `is_confirmed=0` 待复核）
2. `login` — 与卖家会员名完全相同
3. `contains` — 两边规范化后互相包含，且较短一方 ≥4 字、占较长一方 ≥50%（防误判）；命中标记为**待人工复核**（`is_confirmed=0`）
4. `login`（包含）— 销方名称包含卖家会员名
5. `remark` — 发票备注里出现商家名/会员名，或 `1688 XXX` 形式的店铺名线索

匹配不上的名称**不写占位行**，由视图 `v_unmatched_seller_name` 暴露，等人工在「名称映射」页补。再次导入时已映射的名称不再重新匹配。

**名称规范化** `normName()`：去空白（含全角空格）、全半角括号统一、去 `，、;·.-_*` 等标点、转大写。

## 8. 聊天发送核心逻辑（lib/sender.js）

聊天页 URL：`https://air.1688.com/app/ocms-fusion-components-1688/def_cbu_web_im/index.html?touid=cnalichn{卖家登录ID}&siteid=cnalichn&status=1`

1. `openChatReady`：打开 URL + `bringToFront()` → **轮询**等 `def_cbu_web_im_core` iframe 内 `pre.edit[contenteditable="true"]` 出现（找到后 1.6s 再确认一次防 iframe 重建；总等待≥2.5s；单轮 15s 未就绪则 reload，最多 3 轮）。**每次操作前必须重新 getFrame**
2. `ensureContact`：判定右侧空状态文案消失（轮询，最多 8s）；未自动选中则点击左侧会话列表目标项（兜底，不拦截）
3. `sendMessage`（每条）：清残留草稿（Ctrl+A+Delete）→ `keyboard.insertText` 整体插入 → 轮询验证编辑器有内容 → 点 `button.send-btn` → **轮询验证消息尾部30字出现在聊天记录 `pre.edit` 里**（成功判据）；失败重试 1 次
4. 消息之间随机停 1.2~2.5 秒（**仅非最后一条**；最后一条发完即关页）

**性能优化（2026-10-12）**：原实现为固定盲等（编辑器前 8s、每条消息发后 2.5s、消息间 3~5s 且含最后一条），单家约 45s。现全部改为「条件满足即继续」的轮询，**单家发送动作降到约 10~15s（A/B 实测 34.4s → 6.6s，5.2x）**，功能与验证逻辑完全不变。家与家之间的 `sendGapMinSec/MaxSec`（默认 15~30s）是防限流主开关，不在 sender.js 内，可在看板设置页调整。

**健壮性（2026-10-12）**：
- `getFrame/getEditor` 全部容错——iframe 重建瞬间的 detached 异常视为「未就绪」继续轮询，不再让单家整批失败
- **登录态失效快速失败**：就绪等待期间若 URL 跳回 `login.1688.com`，立刻抛「登录态失效」；`doSend` 捕获后**中止整批且不写 send_log**（环境问题，避免污染统计与空转 45s×N）
- 就绪等待有上限（3 轮 ×15s，最多 reload 2 次），卡死的卖家约 45s 后跳过，不会无限等待
- **家间间隔可中断**：`sleep(gap)` 改为 ≤500ms 分段轮询 `stopRequested`，点「停止」在等待期间即时生效（不必干等整个间隔）
- **进度可预期**：`/api/task` 的 `startedAt` + `done/total` 由前端算出「已用/约剩」（按当前实际速率自校准，不依赖配置）

server.js 侧变化：`doSend` 从数据库取会员名（`loadSellers` + `loadSellerDetail`），只把 `invoice_state <> 'issued'` 的订单写进清单（催收口径=会员名级）；发送成功写 `send_log` 表；缺 `seller_login` 的卖家直接跳过（touid 依赖它）；任务日志记录预估总时长与每家实际耗时。

## 9. server.js API 一览

| 方法/路径 | 说明 |
|---|---|
| GET `/` | 控制台页面 |
| GET `/api/data` | **公司级**聚合（订单 + 税务局发票 + 催收），会员名在 `companies[].members` 子树 + 已催收列表 + 发票汇总 + 未匹配名称数；**不含订单明细**（展开时按需拉） |
| GET `/api/seller-detail?loginId=` | 该卖家的订单明细 + 已开票明细 + **催收记录明细（send_log 最近 50 次）**（前端展开行时按需拉取，避免大 payload） |
| GET `/api/collect-history?loginId=` 或 `?company=` | **历史催收记录**（点「催收次数」弹窗用）：每次发送的时间/结果/金额/订单号（发送当时快照，老记录为 NULL），按时间倒序；`company` 维度 = `seller_company` 命中 ∪ 该公司全部会员名 `seller_login` 命中 |
| GET/POST `/api/config` | 读/写配置（GET 会剥掉 `platforms`/`mysql` 凭据段） |
| POST `/api/send` | `{loginIds:[...]}` 启动后台发送任务，立即返回 |
| POST `/api/import` | 重新扫描 data/ 下 Excel 全量导入，同步返回 steps |
| GET `/api/import-log` | 最近 30 条导入日志 |
| GET `/api/mapping` | `{mappings(有效映射), ignored(已忽略), unmatched(待比对视图), sellers, unmatchedCount, ignoredCount}`；datalist 候选用 sellers |
| POST `/api/mapping` | `{taxSellerName, sellerCompany, sellerLogin, note}` 人工保存并回填 `issued_invoice.seller_company`（同时取消该名称的忽略标记） |
| POST `/api/mapping/delete` | `{taxSellerName}` 删除映射并清空回填 |
| POST `/api/mapping/ignore` | `{taxSellerName, ignored}` 忽略（默认 true）/恢复一个销方名称；忽略时 `is_ignored=1`、清空 `seller_company` 回填，恢复时无真实映射则删除该记录 |

**分页（2026-10-12 新增）**：看板公司表与映射页三张表（待比对/已维护/已忽略）均为**前端分页**——数据一次性下发，`PAGER` 状态按 10/20/50/100 条切片渲染，筛选/搜索后自动回第 1 页；顶部统计卡始终按全量计算。当前规模（约 2700 公司 / 900 销方名称）此方案最简单；数据量涨到数万行时再改后端分页（`/api/data`、`/api/mapping` 加 page/size 参数）。
| POST `/api/order-state` | 人工确认已开票：`{orderNo, action:'confirm'\|'cancel'}` 单订单；`{loginId, action:'confirm-all'\|'cancel-all'}` 整卖家批量（confirm-all 只动未开票订单；cancel-all 仅回退 `state_source='manual'` 的行，按 `invoice-status.json` 逐单回推平台状态） |
| GET `/api/task` | 任务进度（前端 2 秒轮询） |
| POST `/api/task/stop` | 停止任务（当前家完成后停） |
| POST `/api/apply` | **返回 410 Gone**（功能已移除，保留以明确提示） |

## 10. 历史踩坑（改代码前必读）

1. **消息逐行炸开**：1688 聊天把多行文本按行拆成多条消息（insertText 也一样）→ 订单清单必须单行「；」分隔，超 450 字再起一条
2. **服务器发送失败三天**：doSend 构造 msgSeller 漏传 `loginId` → touid=undefined → 联系人永不选中。**教训：跨层传参必须断言关键字段**
3. **「AI询盘」推广弹窗**会整层盖住聊天界面且时机随机 → 每次 sendMessage 前点按钮清理（点不掉时 remove `.ant-modal-wrap` DOM）
4. **验证码/滑块**出现时须暂停等人（lib/browser.js 的 waitHuman），不要死循环重试
5. Playwright 1.64 无 `page.waitForTimeout`，用本地 `sleep`
6. curl 传中文 JSON 会乱码，测试须 `--data-binary @file` 或 Node 侧请求
7. **server.js 改完必须重启进程**（改代码不重启 = 没生效）
8. **MySQL 未启动时 server 启动不报错**，只是 `/api/data` 返回 500。`server.listen` 回调里已做 ping 自检并打印提示
9. **`mysql2` 默认 dateStrings=false 会因时区把 DATETIME 漂移**，`db.js` 已统一 `dateStrings:true` + `decimalNumbers:true`
10. **库名无法参数化**，`db.safeDbName()` 用白名单正则校验，拼接前必过
11. **Excel 日期是 1900 序列号**，用 `XLSX.SSF.parse_date_code()` 转**本地时间**再格式化；不要用 `(n-25569)*86400*1000`（会差一个时区）
12. **发票导出有两个 sheet**，只能导「信息汇总表」，导「发票基础信息」会与明细重复计数
13. **导入日志字段 NOT NULL 默认值**：`inserted/skipped/auto_mapped/unmatched` 不传会触发 `Column 'auto_mapped' cannot be null`，`logImport()` 已做 0 兜底
14. **CLI 与看板的发送记录必须同源**：看板「已催收」读 `send_log` 表，`send-messages.js` 早期只写 `sent-log.json` → 命令行发的记录看板看不到。现已统一读写 `send_log`
15. **`send-messages.js` 已依赖数据库**：发送前读 `send_log` 做断点续发判定，DB 未启动会直接报错（catch 里已给启动提示）；`--dry-run` 不碰数据库，可离线预演
16. **老库升级走 `db.migrate()`**：`ensureSchema()` 执行 schema.sql（CREATE IF NOT EXISTS 不会改老表）后，用 information_schema 判断列/索引是否存在再 ALTER，幂等可重复执行。新增列必须同时改 schema.sql **和** migrate()
17. **人工确认状态要「三层防覆盖」**：① `applyInvoiceStatus` 的 UPDATE 带 `state_source <> 'manual'`；② `importOrders` 全量重建时回填 `state_source/state_note`；③ 取消确认时按 `invoice-status.json` 回推平台状态，而不是粗暴置 none
18. **send_log 改为事件日志后**：`INSERT` 不能再带 `ON DUPLICATE KEY UPDATE`（唯一键已删）；CLI 断点续发只认 `result='ok'`，否则失败记录会永久跳过该卖家

## 11. 已知设计取舍

- **提交申请彻底移除**：`/api/apply` 返回 410；订单级「已申请」状态只能靠 `refresh-status.js` 从平台拉取
- **CLI 与看板发送记录同源**：`send-messages.js` 与 `server.js` 都读写 `send_log` 表，「已催收」标记互通；但两者的**候选名单口径不同** —— 看板按「订单表待开票金额 > 0」选人，CLI 按「mtop 申请中发票」聚合选人，且 CLI 另受 `dailySendLimit` 约束
- **两套「已开票」口径并存**：`invoice_order.invoice_state` 是平台侧的订单级状态（含人工确认）；`issued_invoice` 是税务局导出的发票级历史数据。看板分别呈现，**不要混算**（税务局导出无订单号，无法直接关联到订单）。因此「已开票金额/张数」只来自税务局文件；人工确认只改订单状态计数，不影响金额
- **催收次数只计成功**：`send_log` 记录每次发送尝试并标 `result`；统计时 `催收次数 = SUM(result='ok')`、`最近催收时间 = 最近一次 ok 的 sent_at`，失败尝试（`SUM(result<>'ok')`）仅在明细与悬浮提示里展示，**不计入次数**。CLI（`send-messages.js`）本就只在成功时写记录，两侧口径现已一致
- **待开票金额 = max(订单总额 − 已开票金额, 0)**，按映射后的商家名汇总；发票额大于订单额时标记 `overInvoiced`
- **导入是全量重建**：文件夹里的 Excel 是唯一真相，删除文件会连带删除数据；映射表除外
- **订单数据不自动更新**：依赖用户手动导出 xlsx（API 拉全量订单会限流）
- **无并发**：发送任务串行（浏览器操作天然不可并行）
- **发送耗时构成**：单家 = 发送动作（约 10~15s，轮询式，见 §8）+ 家间 `runtime.sendGapMinSec/MaxSec`（默认 15~30s，**防限流主开关**，设置页可调）。看板时长估算 = 家数 ×（间隔均值 + 15s）
- **每任务独立浏览器**：doSend 每次启动全新浏览器用完即关，避免共享浏览器的聊天应用本地状态污染
- **未做分页/虚拟滚动**：2744 家公司 / 2756 个会员名一次性下发聚合结果（约 1.5MB），订单明细改为按需加载；数据量再涨需要加后端分页
